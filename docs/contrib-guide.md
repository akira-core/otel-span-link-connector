# opentelemetry-collector-contrib 新 Connector 貢獻指南

本文件整理了向 [opentelemetry-collector-contrib](https://github.com/open-telemetry/opentelemetry-collector-contrib) 捐贈新 connector 元件所需的規範、結構與流程。

---

## 一、捐贈流程概覽

### 1.1 前提條件

- **先在外部倉庫開發**：contrib 要求新元件先在外部 repo 開發並取得實際使用回饋
- **Sponsor**：需一位 [approver 或 maintainer](https://github.com/open-telemetry/opentelemetry-collector-contrib#contributing) 擔任，且必須與你**不同公司**
- **Code Owners**：至少 3 位，其中至少 1 位為 approver 或 maintainer
- **穩定性等級**：新元件從 `development` 開始，達到條件後再以獨立 PR 升級為 `alpha`

### 1.2 提案步驟

1. 在 contrib repo 使用 [new_component.yaml 模板](https://github.com/open-telemetry/opentelemetry-collector-contrib/issues/new?template=new_component.yaml) 開 Issue
2. 透過 `#otel-collector-dev` Slack 頻道或 Collector SIG 會議尋找 sponsor
3. 湊齊 3 位 code owners（建議來自不同公司）

### 1.3 PR 建議順序

1. **第一個 PR**：結構骨架 — README、config、factory、metadata、doc.go
2. **第二個 PR**：完整 connector 實作 + 測試
3. **第三個 PR**：升級到 alpha、加入 `builder-config.yaml`、執行 `make genotelcontribcol`

## 二、元件必要檔案與結構

### 2.1 目錄結構

```
connector/spanlinkservicegraphconnector/
├── go.mod                          # 獨立 Go module
├── go.sum
├── Makefile                        # include ../../Makefile.Common
├── doc.go                          # //go:generate mdatagen metadata.yaml
├── metadata.yaml                   # mdatagen 元資料
├── config.go                       # Config struct + Validate()
├── factory.go                      # NewFactory + createTracesToMetricsConnector
├── connector.go                    # 主邏輯
├── README.md                       # 含 <!-- status autogenerated section -->
├── documentation.md                # [mdatagen 生成]
├── generated_component_test.go     # [mdatagen 生成]
├── generated_package_test.go       # [mdatagen 生成]
├── internal/
│   ├── metadata/                   # [mdatagen 生成]
│   │   ├── generated_status.go
│   │   ├── generated_telemetry.go
│   │   └── generated_telemetry_test.go
│   └── metadatatest/               # [mdatagen 生成]
└── testdata/
    └── config.yaml                 # 設定載入測試用
```

### 2.2 各檔案說明

| 檔案 | 說明 | 手動/生成 |
|---|---|---|
| `metadata.yaml` | 元件元資料，定義 type、stability、telemetry metrics | 手動 |
| `doc.go` | 含 `//go:generate mdatagen metadata.yaml` 的 package 文件 | 手動 |
| `config.go` | 設定結構體與 `Validate()` 方法 | 手動 |
| `factory.go` | 實作 `connector.Factory` | 手動 |
| `connector.go` | 主要邏輯（`ConsumeTraces` 等） | 手動 |
| `Makefile` | 只需 `include ../../Makefile.Common` | 手動 |
| `README.md` | 含 `<!-- status autogenerated section -->` 區塊 | 手動（部分生成） |
| `documentation.md` | mdatagen 生成，勿手動編輯 | 生成 |
| `generated_*.go` | mdatagen 生成的測試與 metadata | 生成 |
| `internal/metadata/` | mdatagen 生成的 Type、ScopeName、TelemetryBuilder | 生成 |

## 三、metadata.yaml 格式

```yaml
type: spanlinkservicegraph           # 元件名稱
display_name: Span Link Service Graph Connector

status:
  class: connector                   # 元件類型
  stability:
    development: [traces_to_metrics] # 新元件用 development
  distributions: []                  # 捐贈後由 maintainer 決定
  codeowners:
    active: [github-user-1, github-user-2, github-user-3]

tests:
  config:                            # 供 generated_component_test.go 使用

telemetry:
  metrics:
    connector_spanlinkservicegraph_total_edges:
      description: Total number of link edges resolved
      unit: "1"
      enabled: true
      stability: development
      sum:
        value_type: int
        monotonic: true
    # ... 其他自有 telemetry metrics
```

### 3.1 穩定性等級說明

| 等級 | 說明 |
|---|---|
| `development` | 新元件起始等級，API 可能隨時變更 |
| `alpha` | 功能基本穩定，有足夠測試覆蓋 |
| `beta` | 接近穩定，向後相容性有保證 |
| `stable` | 穩定版本 |

## 四、mdatagen 使用方式

### 4.1 設定

在 `doc.go` 中加入：

```go
//go:generate mdatagen metadata.yaml

// Package spanlinkservicegraphconnector provides a connector that derives
// service graph metrics from span links.
package spanlinkservicegraphconnector
```

### 4.2 執行

```bash
# 在元件目錄中執行
make generate
# 或
go generate ./...
```

### 4.3 生成的檔案

- `internal/metadata/generated_status.go` — `Type`、`ScopeName`、`TracesToMetricsStability`
- `internal/metadata/generated_telemetry.go` — `TelemetryBuilder`
- `internal/metadata/generated_telemetry_test.go`
- `internal/metadatatest/` — telemetry 測試輔助
- `generated_component_test.go` — `TestComponentFactoryType`、`TestComponentConfigStruct`、`TestComponentLifecycle`
- `generated_package_test.go` — `goleak.VerifyTestMain(m)`
- `documentation.md` — 自動生成的文件
- `README.md` 中的 status 區塊

### 5.1 Traces-to-Metrics Connector 介面

```go
// connector.Traces = component.Component + consumer.Traces
type Traces interface {
    component.Component      // Start(ctx, host) + Shutdown(ctx)
    consumer.Traces          // ConsumeTraces(ctx, ptrace.Traces) error

```

### 5.2 Factory 建立

```go

        ),
    )
}

func createTracesToMetricsConnector(
```

## 六、測試要求

### 6.1 覆蓋率目標

- **至少 80%** 程式碼覆蓋率

### 6.2 必要測試類型

| 測試類型 | 檔案 | 工具 |
|---|---|---|
| Config 載入 | `config_test.go` | `confmaptest.LoadConf()` + `sub.Unmarshal(cfg)` |
| Config 驗證 | `config_test.go` | `cfg.Validate()` 錯誤情境 |
| Factory | `factory_test.go` | `factory.CreateTracesToMetrics()` |
| Golden test | `connector_test.go` | `golden.ReadTraces()` + `pmetrictest.CompareMetrics()` |
| 元件生命週期 | `generated_component_test.go` | mdatagen 自動生成 |
| Goroutine leak | `generated_package_test.go` | `goleak.VerifyTestMain(m)` |

### 6.3 Golden Test 模式

```go
func TestConnectorConsumeTraces(t *testing.T) {
    // 1. 讀取輸入 traces
    traces, err := golden.ReadTraces("testdata/kafka-link-trace.yaml")
    require.NoError(t, err)

    // 2. 建立 connector
    cfg := createDefaultConfig().(*Config)
    sink := &consumertest.MetricsSink{}
    conn, err := createTracesToMetricsConnector(ctx, params, cfg, sink)
    require.NoError(t, err)

    // 3. 送入 traces
    err = conn.ConsumeTraces(ctx, traces)
    require.NoError(t, err)

    // 4. 取得 metrics 並比對
    expected, err := golden.ReadMetrics("testdata/kafka-link-expected-metrics.yaml")
    require.NoError(t, err)

    actual := sink.AllMetrics()
    require.NoError(t, pmetrictest.CompareMetrics(expected, actual[0],
        pmetrictest.IgnoreTimestamp(),
    ))
}
```

### 6.4 常用測試工具

- `connectortest.NewNopSettings()` — 建立 nop settings
- `consumertest.NewNop()` / `consumertest.MetricsSink` — mock consumer
- `componenttest.NewNopHost()` — mock host
- `golden.ReadTraces()` / `golden.ReadMetrics()` — 讀取 testdata YAML
- `pmetrictest.CompareMetrics()` — 比對 metrics（含 `IgnoreTimestamp` 等選項）

## 八、獨立開發期的注意事項

### 8.1 Go Module 路徑

- 開發期使用自有路徑：`github.com/<org>/otel-span-link-connector/connector/spanlinkservicegraphconnector`
- 捐贈後改為：`github.com/open-telemetry/opentelemetry-collector-contrib/connector/spanlinkservicegraphconnector`

### 8.2 依賴管理

- 使用 `go.opentelemetry.io/collector` 系列套件
- 鎖定與 contrib 相同的 collector 版本

### 8.3 Makefile

開發期可自訂 `Makefile.Common`：

```makefile
# Makefile.Common (repo root)
.PHONY: mdatagen
mdatagen:
	cd connector/spanlinkservicegraphconnector && go generate ./...
```

元件 Makefile：

```makefile
include ../../Makefile.Common
```

### 8.4 獨立使用（OCB）

使用 [OpenTelemetry Collector Builder](https://opentelemetry.io/docs/collector/custom-collector/) 建構自訂 Collector：

```yaml
# builder-config.yaml
dist:
  name: otelcol-custom
  output_path: ./build

connectors:
  - gomod: github.com/<org>/otel-span-link-connector/connector/spanlinkservicegraphconnector v0.1.0
```
